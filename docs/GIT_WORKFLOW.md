# Git Workflow

Branching and commit conventions for the TwinTack rebuild.

## Remote

```bash
git remote add origin https://github.com/misterlinderman/twintackrebuild2026.git
```

Use the **misterlinderman** GitHub account for pushes:

```bash
gh auth switch --user misterlinderman
```

## Branch model

```
main          ← stable, reviewed custom code
  └── develop ← integration branch
        ├── feature/homepage-refactor
        ├── feature/plugin-consolidation
        └── fix/cart-quantity-bug
```

| Branch | Base | Merge target |
|--------|------|--------------|
| `feature/*`, `fix/*` | `develop` | `develop` via PR |
| `develop` | `main` | `main` when release-ready |
| `migration/*` | `main` | `develop` after port complete |

## What belongs in commits

**Include:**

- Custom theme changes under `themes/twintack2025/` (or successor)
- Custom plugin source under `plugins/twintack-*`
- Documentation updates in `docs/`
- Cursor rules in `.cursor/rules/`
- ACF JSON exports in theme if used for field group sync

**Exclude (enforced by `.gitignore`):**

- `uploads/`
- WordPress core
- All third-party plugins (`plugins/*` except `plugins/twintack-*`)
- `wp-config.php`, `.env`, credentials
- `node_modules/`, compiled assets if regenerated by build

Third-party plugins are copied locally from production for parity but must be reinstalled from WP admin or license zips on a fresh clone. Versions are documented in `docs/PLUGIN_INVENTORY.md`.

## Commit message format

```
<type>: <short summary>

Optional body explaining why, not just what.
```

Types: `feat`, `fix`, `refactor`, `docs`, `chore`, `migration`

Examples:

```
feat: add consolidated grip manager admin screen
fix: correct cart fragment on variable product update
migration: port twintack2025 theme from legacy repo
docs: document WooCommerce import steps
```

## Typical workflow

```bash
git checkout develop
git pull origin develop
git checkout -b feature/my-change

# ... edit theme/plugins ...
# Test in Local

git add themes/twintack2025/inc/my-file.php
git commit -m "feat: describe the change"
git push -u origin feature/my-change

gh pr create --base develop --title "feat: describe the change"
```

## Deployment to production (future)

This repo does not auto-deploy. Planned approach:

1. Merge tested `develop` → `main`
2. Deploy `themes/` and custom `plugins/` to production via SFTP, rsync, or hosting Git integration
3. Run any required DB migrations or ACF sync manually
4. Never deploy untested branches directly

Document the production deploy process here once the hosting workflow is chosen.
